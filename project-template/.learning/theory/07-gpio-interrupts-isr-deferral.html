🎯 What are Hardware Interrupts?

Interrupts: Hardware Events That Demand Immediate Attention

Think of interrupts like a doorbell:

  • You're busy doing something (running task code)
  • Doorbell rings (hardware event occurs)
  • You immediately stop what you're doing (CPU pauses current task)
  • Answer the door (execute Interrupt Service Routine - ISR)
  • Return to what you were doing (resume task)

In embedded systems:

  • Button pressed → GPIO interrupt fires
  • Data arrived on UART → UART interrupt fires
  • Timer expired → Timer interrupt fires
  • DMA transfer complete → DMA interrupt fires

❌ Polling (Wasteful)

while(1) { if(button_pressed()) { handle_button(); } vTaskDelay(10); // Check every 10ms } // Problems: // - Wastes CPU checking constantly // - 10ms delay = slow response // - 1ms delay = still wastes 99% CPU // - Miss events between checks

✅ Interrupts (Efficient)

// Task sleeps until signaled while(1) { wait_for_interrupt_signal(); handle_button(); } // ISR (runs on button press): void button_isr() { signal_task(); // Wake up task } // Benefits: // - Zero CPU when idle // - Instant response (microseconds) // - Never miss events

🏗️ The ISR Deferral Pattern

Design Pattern: ISR Deferral / Interrupt Handler

One of the MOST CRITICAL patterns in professional embedded development!

The Golden Rule:

ISRs must be FAST. Defer heavy work to tasks.

Why ISRs Must Be Fast

  1. Other interrupts are blocked - Delays affect whole system responsiveness
  2. Limited stack space - ISR stack is small (often 1KB or less)
  3. FreeRTOS restrictions - Most RTOS functions can't be called from ISR
  4. Flash cache disabled - Code must be in RAM (IRAM_ATTR)
  5. No blocking allowed - Cannot wait, delay, or allocate memory
  6. Watchdog still running - Long ISR can trigger watchdog reset

ISR Deferral Pattern Structure

graph LR A[Hardware Event] -->|Triggers| B[ISR Fast] B -->|Read HW| C[Minimal Data] B -->|Send| D[Queue] D -->|Signals| E[Waiting Task] E -->|Process| F[Heavy Work] style A fill:#ff9800,stroke:#e65100 style B fill:#f44336,stroke:#c62828,color:#fff style D fill:#2196f3,stroke:#1565c0,color:#fff style E fill:#4caf50,stroke:#2e7d32,color:#fff style F fill:#9c27b0,stroke:#6a1b9a,color:#fff

Step 1: ISR (Interrupt Service Routine) - FAST

  • Read hardware register if needed
  • Clear interrupt flag
  • Send minimal data to queue
  • Duration: Microseconds

Step 2: Queue - Thread-Safe Communication

  • Bridges ISR context to task context
  • Buffers multiple events if they arrive quickly
  • Non-blocking send from ISR

Step 3: Task - HEAVY Processing

  • Receives event from queue (blocking wait)
  • Performs complex calculations
  • Logging, printf, ESP_LOGI
  • Updates data structures
  • Calls other functions
  • Duration: Milliseconds OK
Example: ISR Deferral Pattern in Action
// Global queue handle QueueHandle_t button_queue; // ISR - Runs in interrupt context (FAST!) void IRAM_ATTR button_isr_handler(void* arg) { static uint32_t press_count = 0; press_count++; BaseType_t xHigherPriorityTaskWoken = pdFALSE; xQueueSendFromISR(button_queue, &press_count, &xHigherPriorityTaskWoken); if(xHigherPriorityTaskWoken) { portYIELD_FROM_ISR(); // Context switch if higher priority task woken } // ISR exits here - total time: ~2-5 microseconds } // Task - Runs in task context (Can be slow) void buttonTask(void* pvParameter) { uint32_t press_count; bool led_state = false; while(1) { // Block here waiting for interrupt event if(xQueueReceive(button_queue, &press_count, portMAX_DELAY) == pdTRUE) { // Heavy processing allowed here: led_state = !led_state; gpio_set_level(LED_GPIO, led_state); ESP_LOGI("BUTTON", "Press #%lu - LED %s", press_count, led_state ? "ON" : "OFF"); vTaskDelay(pdMS_TO_TICKS(50)); // Debounce delay } } }

🧠 IRAM_ATTR: Why ISRs Need Special Memory

The Flash Cache Problem

ESP32 stores your program in external flash memory. For speed, it caches flash contents in RAM.

During an interrupt:

  • Flash cache is DISABLED (to maintain consistency)
  • CPU cannot read code from flash
  • If your ISR is in flash → CRASH!

Solution: IRAM_ATTR

Forces the function to be placed in Internal RAM (IRAM), not flash.

Using IRAM_ATTR
// ❌ WRONG - ISR in flash (will crash) void button_isr_handler(void* arg) { // This code is in FLASH! } // ✅ CORRECT - ISR in RAM void IRAM_ATTR button_isr_handler(void* arg) { // This code is in IRAM - safe during interrupt }

What Functions Need IRAM_ATTR?

Function Type Needs IRAM_ATTR?
ISR handlers (registered with gpio_isr_handler_add) YES - Required!
Functions called FROM ISR YES - Required!
Regular task functions No - Can be in flash
FreeRTOS FromISR functions No - Already in IRAM

📝 Designated Initializers (C99 Feature)

Modern C: Named Struct Initialization

Designated initializers let you initialize struct members by name, making code self-documenting.

❌ Old Way: Positional Initialization

gpio_config_t conf; conf.pin_bit_mask = (1ULL << 15); conf.mode = GPIO_MODE_INPUT; conf.pull_up_en = GPIO_PULLUP_DISABLE; conf.pull_down_en = GPIO_PULLDOWN_ENABLE; conf.intr_type = GPIO_INTR_POSEDGE; // Or even worse: gpio_config_t conf = { (1ULL << 15), GPIO_MODE_INPUT, 0, 1, GPIO_INTR_POSEDGE }; // What's 0? What's 1?

✅ New Way: Designated Initializers

gpio_config_t conf = { .pin_bit_mask = (1ULL << GPIO_NUM_15), .mode = GPIO_MODE_INPUT, .pull_up_en = GPIO_PULLUP_DISABLE, .pull_down_en = GPIO_PULLDOWN_ENABLE, .intr_type = GPIO_INTR_POSEDGE }; // Crystal clear! // Self-documenting // Order doesn't matter // Unspecified fields = 0

Benefits of Designated Initializers

  • ✅ Readable: See what each value means
  • ✅ Safe: Compiler error if field name wrong
  • ✅ Flexible: Can omit fields (default to 0)
  • ✅ Order-independent: Write in any order
  • ✅ Maintainable: Adding struct fields won't break code

🔄 FreeRTOS FromISR Functions

Critical Rule: Use FromISR Versions in Interrupts!

Regular FreeRTOS functions are NOT SAFE to call from ISR context.

Always use the FromISR variants:

Regular Function (Task Context) ISR-Safe Version (Interrupt Context)
xQueueSend() xQueueSendFromISR()
xSemaphoreGive() xSemaphoreGiveFromISR()
xTaskNotifyGive() vTaskNotifyGiveFromISR()
xEventGroupSetBits() xEventGroupSetBitsFromISR()
xQueueSendFromISR() Explained
void IRAM_ATTR button_isr_handler(void* arg) { uint32_t event_data = 42; // This variable tracks if a higher-priority task was woken BaseType_t xHigherPriorityTaskWoken = pdFALSE; // Send to queue (non-blocking in ISR) xQueueSendFromISR( button_queue, // Queue handle &event_data, // Pointer to data to send &xHigherPriorityTaskWoken // Updated if task woken ); // If a higher-priority task was woken, request context switch if(xHigherPriorityTaskWoken) { portYIELD_FROM_ISR(); // Switch to that task immediately after ISR } } // Why xHigherPriorityTaskWoken? // - Queue might wake a task that was blocked waiting for data // - That task might be higher priority than current running task // - We want to switch to it ASAP (not wait until next scheduler tick) // - portYIELD_FROM_ISR() requests immediate context switch

Key Differences: FromISR vs Regular

  • No blocking: FromISR functions never block (return immediately)
  • Context switch tracking: Track if higher-priority task woken
  • Simplified: No timeout parameter (always immediate)
  • IRAM-safe: FromISR functions are in IRAM

🔢 Bit Manipulation: ULL and GPIO Masks

Why (1ULL << GPIO_NUM)?

ESP32 has up to 40 GPIOs. A bitmask needs 64 bits to represent all of them.

ULL Suffix Explained
// ULL = Unsigned Long Long (64-bit integer) // ❌ WRONG: Using regular int (32-bit) #define GPIO_NUM 35 int mask = (1 << GPIO_NUM); // Shift left 35 positions // Problem: 1 is 32-bit int, shifting left 35 positions = OVERFLOW! // Undefined behavior // ✅ CORRECT: Using ULL (64-bit) uint64_t mask = (1ULL << GPIO_NUM); // 1ULL is 64-bit // Binary: 0000...0001000000000000000000000000000000 (bit 35 set) // Safe for any GPIO number 0-39
Multiple GPIOs in One Bitmask
// Configure multiple GPIOs at once using bitwise OR gpio_config_t conf = { .pin_bit_mask = (1ULL << GPIO_NUM_15) | (1ULL << GPIO_NUM_16) | (1ULL << GPIO_NUM_17), .mode = GPIO_MODE_INPUT, // ... }; // Binary representation: // GPIO 15: 0000...0000000000000001000000000000000 // GPIO 16: 0000...0000000000000010000000000000000 // GPIO 17: 0000...0000000000000100000000000000000 // OR'd: 0000...0000000000000111000000000000000 // ^^^ // Bits 15,16,17 set

C Integer Suffixes

Suffix Type Size Example
(none) int 32-bit 1, 42, 1000
U unsigned int 32-bit 1U, 42U

ULL unsigned long long 64-bit 1ULL, 42ULL

🔘 Button Debouncing

The Bouncing Problem

Mechanical buttons don't make clean electrical contact. When pressed:

  • Contacts physically bounce (vibrate) for 5-20ms
  • Creates multiple rapid HIGH-LOW transitions
  • Microcontroller sees 5-10 "presses" for one physical press
sequenceDiagram participant B as Button participant G as GPIO participant ISR as ISR Note over B: User presses button B->>G: HIGH G->>ISR: Interrupt 1 B->>G: LOW (bounce) B->>G: HIGH (bounce) G->>ISR: Interrupt 2 B->>G: LOW (bounce) B->>G: HIGH (bounce) G->>ISR: Interrupt 3 B->>G: Stable HIGH Note over ISR: 3 interrupts from 1 press!

Software Debouncing Solutions

Solution 1: Delay After Event (Simple)

void buttonTask(void* pvParameter) { while(1) { xQueueReceive(button_queue, &event, portMAX_DELAY); // Process button toggle_led(); // Ignore all events for 50ms vTaskDelay(pdMS_TO_TICKS(50)); // Clear any bounces that arrived during delay xQueueReset(button_queue); } }

Solution 2: Timestamp Checking (Better)

void buttonTask(void* pvParameter) { uint32_t last_press_time = 0; const uint32_t debounce_ms = 50; while(1) { xQueueReceive(button_queue, &event, portMAX_DELAY); uint32_t now = xTaskGetTickCount() * portTICK_PERIOD_MS; if((now - last_press_time) > debounce_ms) { // Valid press toggle_led(); last_press_time = now; } else { // Bounce - ignore } } }

Solution 3: Hardware Debouncing

  • RC filter (resistor + capacitor) on button line
  • Schmitt trigger IC
  • More reliable but costs hardware

Complete GPIO Interrupt Configuration
// Step 1: Configure GPIO with interrupt gpio_config_t button_conf = { .pin_bit_mask = (1ULL << BUTTON_GPIO), // Which pin(s) .mode = GPIO_MODE_INPUT, // Input or output .pull_up_en = GPIO_PULLUP_DISABLE, // Internal pull-up .pull_down_en = GPIO_PULLDOWN_ENABLE, // Internal pull-down .intr_type = GPIO_INTR_POSEDGE // Interrupt trigger }; gpio_config(&button_conf); // Step 2: Install interrupt service (do once globally) gpio_install_isr_service(0); // 0 = default flags // Step 3: Register ISR handler for specific GPIO gpio_isr_handler_add( BUTTON_GPIO, // GPIO number button_isr_handler, // ISR function (void*)BUTTON_ID // Argument passed to ISR );

GPIO Interrupt Types

Interrupt Type Triggers When Use Case
GPIO_INTR_DISABLE Never No interrupt
GPIO_INTR_POSEDGE LOW → HIGH transition Button press (active high)
GPIO_INTR_NEGEDGE HIGH → LOW transition Button release, or active low
GPIO_INTR_ANYEDGE Any transition Rotary encoder, frequency measurement
GPIO_INTR_LOW_LEVEL While LOW Continuous detection
GPIO_INTR_HIGH_LEVEL While HIGH Continuous detection

Pull-Up vs Pull-Down Resistors

Why do we need them? Floating inputs read random values!

Pull-Down (Button to 3.3V):

  • Resistor connects GPIO to GND
  • GPIO reads LOW when button not pressed
  • Button press connects GPIO to 3.3V → HIGH
  • Use GPIO_INTR_POSEDGE to detect press

Pull-Up (Button to GND):

  • Resistor connects GPIO to 3.3V
  • GPIO reads HIGH when button not pressed
  • Button press connects GPIO to GND → LOW
  • Use GPIO_INTR_NEGEDGE to detect press

⚠️ Common Mistakes & How to Avoid Them

Mistake #1: Forgetting IRAM_ATTR

// ❌ WRONG void button_isr_handler(void* arg) { // This will crash randomly! } // ✅ CORRECT void IRAM_ATTR button_isr_handler(void* arg) { // Safe in IRAM }

Symptom: Intermittent crashes, "Cache disabled but cached memory region accessed" error

Mistake #2: Heavy Processing in ISR

// ❌ WRONG void IRAM_ATTR button_isr_handler(void* arg) { ESP_LOGI("ISR", "Button pressed"); // NEVER LOG IN ISR! vTaskDelay(pdMS_TO_TICKS(100)); // NEVER DELAY IN ISR! complex_calculation(); // NEVER DO THIS! } // ✅ CORRECT void IRAM_ATTR button_isr_handler(void* arg) { uint32_t event = 1; BaseType_t xHigherPriorityTaskWoken = pdFALSE; xQueueSendFromISR(queue, &event, &xHigherPriorityTaskWoken); if(xHigherPriorityTaskWoken) portYIELD_FROM_ISR(); // Total: ~3 microseconds }

Symptom: System becomes sluggish, other interrupts missed, watchdog resets

Mistake #3: Using Wrong FreeRTOS Function

// ❌ WRONG void IRAM_ATTR button_isr_handler(void* arg) { xQueueSend(queue, &data, 0); // Regular version - NOT ISR-SAFE! } // ✅ CORRECT void IRAM_ATTR button_isr_handler(void* arg) { BaseType_t xHigherPriorityTaskWoken = pdFALSE; xQueueSendFromISR(queue, &data, &xHigherPriorityTaskWoken); if(xHigherPriorityTaskWoken) portYIELD_FROM_ISR(); }

Symptom: System hangs, assertion failures, queue corruption

Mistake #4: Not Handling Debouncing

// ❌ WRONG void buttonTask(void* pvParameter) { while(1) { xQueueReceive(queue, &event, portMAX_DELAY); counter++; // Will count 5-10 for each physical press! } } // ✅ CORRECT void buttonTask(void* pvParameter) { while(1) { xQueueReceive(queue, &event, portMAX_DELAY); counter++; vTaskDelay(pdMS_TO_TICKS(50)); // Debounce xQueueReset(queue); // Clear bounces } }

Mistake #5: Wrong Bit Width for GPIO Mask

// ❌ WRONG - Overflow for GPIO > 31 gpio_config_t conf = { .pin_bit_mask = (1 << GPIO_NUM_35), // 32-bit overflow! // ... }; // ✅ CORRECT - 64-bit for all GPIOs gpio_config_t conf = { .pin_bit_mask = (1ULL << GPIO_NUM_35), // Safe // ... };

🤔 Critical Thinking Questions

Q1: Why can't you use ESP_LOGI() inside the ISR?

Answer:

  • Logging internally uses printf()
  • printf() allocates memory from heap
  • Memory allocation uses mutexes (can block)
  • ISRs cannot block or wait
  • String formatting is slow (milliseconds)
  • UART transmission is slow
  • Would make ISR 1000x slower than it should be!

Q2: What happens if you forget IRAM_ATTR on your ISR?

Answer:

  • ISR code remains in external flash memory
  • When interrupt fires, CPU tries to execute from flash
  • But flash cache is disabled during interrupts!
  • CPU gets "Cache disabled but cached memory region accessed" error
  • System crashes or reboots
  • Might work sometimes (if code happens to be cached)
  • Unreliable, intermittent failures - worst kind of bug!

Q3: Why use a queue instead of a global flag variable?

Answer:

  • Lost events: Flag can only hold one state. Multiple quick presses lost.
  • Race conditions: ISR sets flag, task clears it - timing issues possible.
  • No queuing: Can't buffer events that arrive faster than task processes.
  • Thread safety: Queue is designed for ISR→Task communication, flags aren't.
  • Blocking wait: Task can efficiently wait on queue (zero CPU), flags require polling.
// ❌ Global flag approach (loses events): volatile bool button_pressed = false; // Only holds 1 event ISR: button_pressed = true; // Press 1 ISR: button_pressed = true; // Press 2 (overwrites!) ISR: button_pressed = true; // Press 3 (overwrites!) Task reads once: button_pressed = false; // 2 presses LOST! // ✅ Queue approach (no losses): ISR: xQueueSend(queue, 1); // Press 1 queued ISR: xQueueSend(queue, 2); // Press 2 queued ISR: xQueueSend(queue, 3); // Press 3 queued Task: Receive all 3 events in order

Q4: How would you handle 3 different buttons using one ISR?

Answer:

// Pass button ID as ISR argument #define BUTTON1_ID 1 #define BUTTON2_ID 2 #define BUTTON3_ID 3 void IRAM_ATTR button_isr_handler(void* arg) { uint32_t button_id = (uint32_t)arg; // Retrieve which button BaseType_t xHigherPriorityTaskWoken = pdFALSE; xQueueSendFromISR(queue, &button_id, &xHigherPriorityTaskWoken); if(xHigherPriorityTaskWoken) portYIELD_FROM_ISR(); } // Register same ISR for all buttons, different args: gpio_isr_handler_add(GPIO_NUM_15, button_isr_handler, (void*)BUTTON1_ID); gpio_isr_handler_add(GPIO_NUM_16, button_isr_handler, (void*)BUTTON2_ID); gpio_isr_handler_add(GPIO_NUM_17, button_isr_handler, (void*)BUTTON3_ID); // Task receives button ID and handles accordingly: void buttonTask(void* pvParameter) { uint32_t button_id; while(1) { xQueueReceive(queue, &button_id, portMAX_DELAY); switch(button_id) { case BUTTON1_ID: handle_button1(); break; case BUTTON2_ID: handle_button2(); break; case BUTTON3_ID: handle_button3(); break; } } }

Q5: What's the tradeoff between interrupt-driven and polling?

Answer:

Interrupts (Event-Driven):

  • ✅ Zero CPU when idle - power efficient
  • ✅ Instant response (microseconds)
  • ✅ Never miss events
  • ❌ More complex code
  • ❌ ISR restrictions (IRAM, no blocking, etc.)
  • ❌ Harder to debug

Polling (Query Periodically):

  • ✅ Simple code - just check in loop
  • ✅ Easy to debug
  • ✅ No ISR restrictions
  • ❌ Wastes CPU (checking constantly or frequently)
  • ❌ Slower response (depends on poll rate)
  • ❌ Can miss short events between polls

When to use each:

  • Interrupts: Critical timing, low-power, fast events, high-frequency signals
  • Polling: Learning/prototyping, slow sensors, when simplicity matters more than efficiency

✅ Best Practices Summary

ISR Golden Rules

  1. ALWAYS use IRAM_ATTR on ISR functions
  2. ALWAYS keep ISRs fast (< 10 microseconds ideal)
  3. ALWAYS use FromISR variants of FreeRTOS functions
  4. NEVER log, print, or allocate memory in ISR
  5. NEVER call blocking functions (delays, mutexes, etc.)
  6. NEVER do complex calculations in ISR
  7. DEFER all heavy work to tasks via queues

GPIO Configuration Checklist

  • ✅ Use designated initializers for clarity
  • ✅ Use ULL suffix for GPIO masks (64-bit)
  • ✅ Configure pull-up/pull-down to avoid floating inputs
  • ✅ Choose correct interrupt type (POSEDGE vs NEGEDGE)
  • ✅ Call gpio_install_isr_service() once before adding handlers
  • ✅ Check return values of all GPIO functions

Debouncing Strategies

  • ✅ Software: Add 50ms delay after event in task
  • ✅ Software: Check timestamp of last press before processing
  • ✅ Hardware: RC filter on button line
  • ✅ Clear queue after debounce delay to remove bounces
